MISS CLAUDE — MULTI-SESSION WORKTREE ROLES & GUARDRAILS


PURPOSE

The operator runs many Claude Code sessions at once and is NOT a git expert. These guardrails exist
to keep the operator from making mistakes, not to teach git. Every session: speak plain English, keep
it short, and end every reply with the STATUS block below.

The short version lives in CLAUDE.md ("Roles & branch workflow"). This file is the full reference.


WHAT THIS REPO IS

  Miss Claude (a.k.a. the Mission Dashboard) — a dependency-free, Python-3-stdlib web UI served by
  two systemd units:
    mission-dashboard.service   the HTTP app (app.py, port 4200)
    claude-console.service      the ttyd Claude-console bridge (port 4201)
  "Application code" = app.py, the console-*.sh / install.sh scripts, the *.service units, and
  anything under scripts/. There is no build step; "deploy" means restart the service (below).


PLAIN LABELS

  feature worker   a normal coding session, in its own worktree on a claude/<slug> branch
  integrator       the one session that accepts finished branches into staging
  staging          the `working` branch (integration branch)
  deploy branch    the `main` branch (release; what the live services run from)


BRANCH MODEL

  working (staging) --ff--> main (deploy branch) --deploy--> live service restart

  Feature workers branch off `working` into ~/missclaude-worktrees/<slug> on claude/<slug>.
  A finished branch is fast-forwarded into `working`, then `working` -> `main` (release), then
  deployed. For normal work those are NOT separately approved: ONE `YES SHIP` runs the whole
  path via scripts/miss-ship.py. The integrator console remains for hand-driven work.


WHAT "DEPLOY" MEANS HERE

  No build, no remote push to a prod box. Deploy = make the running services load the committed code:
    sudo systemctl restart mission-dashboard.service     # app.py changes (port 4200)
  console-session.sh / console-launch.sh changes are picked up by the NEXT console session opened
  (no restart needed); restart claude-console.service only to change ttyd itself, and note that
  restarting it ends live console sessions. Deploy happens as the deploy step of a YES SHIP
  (scripts/miss-ship.py runs it), or by hand in the integrator console after YES DEPLOY. The hook
  does NOT block systemctl for feature workers — not restarting the live service by hand is a
  behavioural rule, not a hard one.


HOW A SESSION KNOWS ITS ROLE

  Launch wrappers export CLAUDE_MISS_ROLE:
    scripts/claude-miss             -> feature   (creates/enters a worktree; FEATURE WORKER banner)
    scripts/claude-miss-integrator  -> integrator(runs in the primary checkout on `working`)
  If CLAUDE_MISS_ROLE is unset, assume feature worker (the restrictive default).


THE STATUS BLOCK (every reply to the operator ends with it, the first of a session included)

  STATUS:
  GREEN / YELLOW / RED / SHIPPED / BLOCKED

  WHAT MATTERS:
  1-3 short bullets maximum.

  NEXT STEP:
  Exactly what the operator types or does next, or None.

  NEEDS APPROVAL:
  Only list an approval phrase if one is actually required.

  Stoplight:
    GREEN   — safe to continue.
    YELLOW  — needs an approval phrase before continuing.
    RED     — stop and ask the integrator / operator.
    SHIPPED — done; nothing for the operator to do.
    BLOCKED — stopped before anything changed.


OUTPUT STYLE (both roles)

  Short, plain English, decision-first: tell the operator only what they need to make the next
  decision or understand the result. Aim at 5-10 lines, fewer for routine success. No jargon,
  no repetition, no restating the request, no explaining internal mechanics.

  Include technical detail ONLY when: something failed; there is meaningful risk; the operator
  must choose between options; or they asked. Otherwise test logs, diffs, commit lists and
  implementation commentary stay in the mission LOG / <mission>/ship.log for later inspection.

  Examples:
    Feature done   STATUS: GREEN
                   WHAT MATTERS: Feature implemented. / Tests pass. / Ready to ship.
                   NEXT STEP: YES SHIP
    Routine ship   STATUS: SHIPPED
                   WHAT MATTERS: Integrated, released, deployed, and verified successfully.
                   NEXT STEP: None
    Blocked        STATUS: BLOCKED
                   WHAT MATTERS: The branch is behind `working` and cannot fast-forward. /
                                 Nothing was changed.
                   NEXT STEP: None — I rebase onto `working`, re-check, and re-run the
                              ship script under the YES SHIP you already gave

  Brevity never weakens safety: the approval phrases below stay exact and required ("ok" is
  never enough), RED still means stop, and anything the operator needs for an INFORMED approval
  — a real risk, a destructive or irreversible step, a caveat that would change their answer —
  is still said, in one short line rather than three paragraphs.


APPROVAL PHRASES (operator must type EXACTLY; nothing vaguer counts)

  YES SHIP           feature worker may ship this branch: commit -> integrate -> push ->
                     release -> deploy -> verify, run end to end by scripts/miss-ship.py.
                     THE ONLY PHRASE A NORMAL SHIPMENT NEEDS.
  YES COMMIT         feature worker may commit mid-work, without shipping
  (no rebase phrase)  a rebase onto current `working` is covered by YES SHIP; the feature
                     worker decides whether one is needed
  YES INTEGRATE      integrator may fast-forward a reviewed feature branch into `working`
  YES PUSH WORKING   integrator may push `working` to origin (if a remote is ever added)
  YES RELEASE        integrator may move `main` forward to `working`
  YES DEPLOY         integrator may restart the service to load the released code

  The four integrator phrases belong to the INTEGRATOR CONSOLE doing hand-driven or recovery work.
  Never ask for one of them (or for YES COMMIT) as a follow-up to a YES SHIP: the operator approved
  the shipment, not its stages. If a step fails, report BLOCKED / NEEDS_ATTENTION and stop.

  "ok", "do it", "sounds good", "continue", "fix it" are NOT enough. Ask for the exact phrase.
  These phrases are enforced by Claude's behaviour — the hook cannot read the chat.


FEATURE WORKER — rules

  May:
    - edit project code in ITS OWN worktree
    - run app.py locally / lint / syntax-check / other checks
    - show a plain-English summary
    - after YES COMMIT (or as part of a YES SHIP): git add by explicit path + git commit
      (never `git add .` / `-A`)
    - as part of a YES SHIP, when the branch has fallen behind: rebase onto current `working`
      (its own call — no separate phrase)
    - after YES SHIP: run scripts/miss-ship.py — the only route by which it reaches
      integrate / push / release / deploy
  Must not (BY HAND, in any case):
    - update `working` (staging)
    - touch `main` (deploy branch)
    - push
    - deploy / restart services (sudo systemctl)
    - edit or clean up other worktrees
    - make git changes outside its own branch


  Shipping (ONE phrase; you never open the integrator console for normal work):
    When the work is verified the worker asks for YES SHIP — and asks for nothing after it.
    It commits its own changes (YES SHIP covers the commit), then runs ONE script:

      python3 scripts/miss-ship.py --approval "YES SHIP" \
          --request "<the request, in plain words>" --tests "<checks run + results>"

    That script performs the rest itself, in order: integrate (--ff-only into the
    integration branch, in the checkout that holds it) -> push (if the repo has a remote)
    -> release -> deploy -> verify. Release/deploy/verify are ONLY the command strings the
    repo already defines in ~/.miss-claude/ship.json (Miss Claude's own repo carries a
    built-in default). A repo that defines none stops after the last established step —
    nothing is ever invented.

    It decides nothing: scope is the mission's recorded repo/branch/base plus the commit the
    branch is on when it starts, and every step re-reads git immediately before it runs. If
    the branch moves off the approved commit mid-run, it stops (NEEDS_ATTENTION) rather than
    ship something the operator did not approve.

    It is idempotent and resumable: a step is skipped when git already shows it done (the
    integration branch contains the commit, the remote ref is at it, the release branch is at
    it), and the deploy — which git cannot see — is recorded per commit in
    ~/.miss-claude/ship/<repo_id>--<branch>.json. If a run dies half way, run the SAME command
    again: it resumes at the first incomplete step and repeats no push, release or deployment.

    Its last line is the report; the worker relays it and stops:
      RESULT: SHIPPED           what is where now (staging / remote / released / deployed / verified)
      RESULT: BLOCKED           a pre-check failed before anything changed; the reason says what to do
      RESULT: NEEDS_ATTENTION   something changed and something did not — a human looks first

    Pre-checks that block with nothing changed: uncommitted changes; not a claude/* branch;
    nothing to ship; branch behind the integration branch (the worker rebases, re-checks and
    re-runs the script under the same YES SHIP); integration checkout on another branch, dirty, or can't be auto-created. A
    missing integration checkout is bootstrapped automatically, not a blocker.

    The worker never gains integrator power itself: the hook still blocks hand-run push /
    merge (sudo itself is allowed), with one carve-out for a plain, unchained run of miss-ship.py.
    Everything the script does is logged (<state>.log, mirrored to <mission>/ship.log).

INTEGRATOR — rules

  For HAND-DRIVEN and RECOVERY work only — normal shipments run themselves (see above).
  Does not write feature code. Reviews and integrates finished branches.
  Before integrating, confirm: branch is clean, based on current `working`, changed files are expected.
  May:
    - review feature branches (diff, log, status)
    - after YES INTEGRATE: git merge --ff-only <claude/branch>   (fast-forward only)
    - after YES PUSH WORKING: git push origin working   (if a remote exists)
    - after YES RELEASE: move `main` forward to `working`
    - after YES DEPLOY: restart the service (sudo systemctl restart mission-dashboard.service)
  Must not:
    - write feature code (*.py, *.sh, *.service, scripts/)
    - force-push (ever)
    - do non-fast-forward merges

  If a branch will not fast-forward, it is behind `working`. Do NOT rebase it yourself — tell the
  operator to have that branch's feature worker rebase it (its YES SHIP covers that), then re-check.


HARD ENFORCEMENT (the hook)

  .claude/hooks/prevent-misswork.py is a PreToolUse hook and the ONLY hard guardrail, because the
  wrappers launch Claude with --dangerously-skip-permissions (the permission allowlist is bypassed).
  It reads CLAUDE_MISS_ROLE and hard-blocks (exit 2) the forbidden actions:

    main/master (any role): the full dangerous set (commit/push/add/reset/rebase/merge/restart/
                            pip/rm/mv/cp/chmod/chown/sudo/redirects/...).
    feature worker:         push, merge, git worktree, branch delete/rename,
                            switching away from its branch; and edits to other worktrees or the
                            primary checkout. (git add/commit/rebase, running app.py, edits in its own
                            worktree, sudo, and /tmp writes stay allowed — the YES phrases gate
                            the rest; a sudo'd push is still judged and blocked; systemctl is not
                            a hook rule.)
                            ONE carve-out: a plain, unchained run of scripts/miss-ship.py, the
                            deterministic YES SHIP path, which enforces its own scope.
    integrator:             editing application code (*.py *.sh *.service scripts/), force-push,
                            non-ff merge, rebase. (docs/ and .claude/ edits are allowed.)

  The hook is a backstop. The role discipline and approval phrases are still your responsibility.


LAUNCH WRAPPERS (scripts/, run from the repo)

  scripts/claude-miss              feature worker. Inside a worktree -> enter & launch. Elsewhere ->
                                   prompt for a task name, create ~/missclaude-worktrees/<slug>
                                   + claude/<slug> off working, then launch. Prints the FEATURE WORKER
                                   banner + stoplight status.
  scripts/claude-miss-integrator   integrator. Runs in ~/mission-dashboard on `working`;
                                   refuses elsewhere. Prints the INTEGRATOR banner and working status.

  Preview either without starting a session:  CLAUDE_MISS_DRYRUN=1 scripts/claude-miss
